# What kyu-runner gets from chassis

> Generated by `chassis sync` from chassis 2.0.0. Do not edit
> by hand: the next `chassis sync --write` overwrites it. It describes the
> kit at that version; it matches this project as long as `chassis_tag` in
> `.chassis.toml` reads `v2.0.0`.

kyu-runner is built on [chassis](https://github.com/kennypassenier/chassis-rs), a shared foundation
for small Rust web services. Everything below comes from the kit and works
the same way in every service built on it. What kyu-runner does itself —
its routes, its pages, its own configuration — is described in the
project's own README and `docs/`.

**This binary is built with: core, self-update.** The kit can do
more than this document describes; what a feature this project does not
build would have added is left out here rather than explained as though it
were there.

## The door: how clients get in

The kit's door — client tokens, the admin token, the sealed client store —
comes with the `dashboard` feature, which kyu-runner is not built with. The
kit adds no authentication of its own here: every route this binary serves
is one the project registered itself, and whatever protects it is the
project's own. `KYU_RUNNER_SECRET_KEY` and `KYU_RUNNER_TOKEN` are not
read, and `gen-secret` is not part of this binary.

To get a token FROM another service built on the kit (a hub this service
calls), use `chassis clients issue <name> --url <base> --token-env <VAR>`
on the machine that runs it; that command talks to the other service's
API, not to this one.

## Health and metrics

`GET /healthz` is open and answers JSON with the running version and one
entry per subsystem. It is HTTP 200 while everything is fine and **503**
as soon as one subsystem reports a failure (`"status":"degraded"`):

```bash
curl -sS http://127.0.0.1:8080/healthz
# {"status":"ok","version":"0.1.0","subsystems":{"store":{"detail":"writable","ok":true}}}
```

`GET /metrics` is open and serves Prometheus text: request counts per
route and status, build info, uptime, and whatever kyu-runner appends.

`kyu-runner --healthcheck` probes `/healthz` of the running instance from
the command line (the container `HEALTHCHECK` and the systemd unit use it)
and exits 0 when a well-formed report came back — degraded still counts
as alive; dead does not.

The project's own numbers go on the same page. `Counter` and `Gauge` from the
kit format the exposition text, so a label value with a quote in it cannot
invalidate the whole scrape — which would take the kit's own metrics with it:

```rust
let delivered = Counter::new(&spec.metric_prefix(), "deliveries_total", "Messages delivered.");
app.metrics_source(delivered.clone());
delivered.inc(&[("topic", "alerts")]);
```

## Self-update (`self-update` feature)

The service can fetch its own next release, verify it and swap the binary
in place. `KYU_RUNNER_UPDATE_MODE` picks who pulls the trigger:

- `off` (default): the status page shows whether a newer release exists;
  nothing is installed.
- `supervised`: the homelab runs `kyu-runner update` on its schedule. That
  one run verifies, installs and exits **0 whether or not anything
  changed** (`already current` is a success); it never restarts the
  service — the supervisor does, after `installed …`.
- `autonomous`: the running process checks on a timer, installs, exits 0
  and lets `Restart=always` start the new binary; a version that does not
  come up healthy is rolled back to the previous binary.

Every release is verified against the **signing key baked into the
binary** before a single byte of it is trusted: the manifest's signature
first, then the binary's SHA-256 against that manifest. A release that
does not verify is refused with nothing installed.

`KYU_RUNNER_UPDATE_HOLD` pins a version (`1.4.0`) or skips one
(`skip:1.4.0`); `KYU_RUNNER_UPDATE_DRILL` is for the broken-release
drill only. Before an update the kit keeps a copy of the state under
`/appdata/kyu/kyu-runner-config-pre-update/<version>/`.

## Command-line controls

| Command | What it does |
|---|---|
| `kyu-runner --version` | Prints `kyu-runner <version>`; reads nothing else. |
| `kyu-runner --check` | Validates the configuration and the project's own checks; opens no socket; exit 0 or 1. |
| `kyu-runner --print-config` | Every knob with its effective value and where it came from (flag, env, file, default); secrets masked. |
| `kyu-runner --knobs` | The table below, for the version of the kit this binary was built with. |
| `kyu-runner --healthcheck [URL]` | Probes `/healthz` of the running instance; exit 0 when alive. |
| `kyu-runner update` | One supervised update attempt; exit 0 when current or installed. |
| `kyu-runner --help` | Every flag, including one per knob. |

## What each feature brings with it

A feature is not only a switch: it pulls in other features, dependencies and
bytes. The chain, so a decision to turn one on can be taken with the cost in
view:

| Feature | Pulls in | What it adds |
|---|---|---|
| `core` | — | configuration, logging, `/healthz`, `/metrics`, shutdown, guards. Always on. |
| `assets` | `core` | the vendored kp-themes tree: stylesheets, scripts and **73 font faces, about 5 MB**, embedded in the binary. |
| `dashboard` | `core`, `assets` | the login page, the KYU_RUNNER admin session, the Clients page and the clients API — **and two mandatory secrets** (see below). |
| `passkeys` | `dashboard`, `assets`, `core` | passkey registration and login; pulls OpenSSL, so a static build would have to vendor it. |
| `self-update` | `core` | the updater, its state and the `update` subcommand; pulls a signature verifier. |
| `notify` | `core` | the webhook notifier and the `[[notify.webhook]]` section. |
| `testing` | `dashboard` (and so `assets`, `core`) | the in-process test harness, for `[dev-dependencies]`. It does not reach the built binary. |

**A feature can make a secret mandatory.**
`dashboard` is the one that does: it makes `<PREFIX>_TOKEN` and
`<PREFIX>_SECRET_KEY` required, and a service that has neither refuses to
start. This binary does not build it, so neither secret is read here — turning
it on later means generating both before the next start.


## Configuration knobs

The project's own settings live in the same config file and are none of the
kit's business: `app.project_config()` hands the project everything the kit
does not own, table sections included.

Every knob answers to three names: a flag, an environment variable and a
key in the config file (`/appdata/kyu/kyu-runner-config/config.toml`). Precedence is
**flag > env > file > default**. Secret knobs have no flag and are refused
from the file. The **Feature** column says which kit feature reads the
knob; a knob of a feature this binary was built without is accepted and
ignored.

## Where things live

- **State**: `KYU_RUNNER_STATE_DIR`, default `/appdata/kyu/kyu-runner-config`. The
  config file and the update state all live under
  this one directory; nothing is written anywhere else.
- **Environment file**: `/appdata/kyu/kyu-runner-config/token.env`, read by the systemd unit
  (`EnvironmentFile=`). It holds any knob you set as
  an environment variable.
- **Pre-update copies**: `/appdata/kyu/kyu-runner-config-pre-update/`, beside the state
  root, not under it.

Everything specific to kyu-runner — its API, its pages, its own settings
and its deployment history — is in this repository's README and the rest
of `docs/`.
